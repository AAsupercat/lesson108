# HTTPS

## HTTPS 就是 HTTP + SSL/TLS层

HTTPS = HTTP + SSL/TLS（安全套接层/传输层安全协议），在HTTP和TCP之间增加了一层加密层。

## 为什么需要HTTPS？

### HTTP协议的安全问题

**HTTP协议是明文传输的**，数据在传输过程中没有任何加密保护，存在严重的安全隐患：

1. **Cookie泄露风险(QQ盗号)**：
   - 用户在浏览器中输入账号、密码等信息，通过Cookie保存
   - HTTP传输时，Cookie以明文形式在网络中传输
   - **中间人攻击（Man-in-the-Middle）**：黑客、恶意WiFi、运营商等中间节点可以轻松截取和查看这些敏感信息

2. **数据篡改(运营商中间链接篡改)**：
   - 中间人可以修改传输的数据
   - 可能插入恶意代码、修改响应内容等

3. **身份冒充(非对称加密缺陷)**：
   - 无法验证服务器的真实身份
   - 可能连接到伪造的服务器

## SSL/TLS 介绍

**SSL（Secure Sockets Layer）安全套接层**：
- 全称：安全套接层
- 开发：由Netscape公司于1994年开发
- 版本：SSL 1.0（未发布）、SSL 2.0、SSL 3.0
- 状态：已被TLS取代，SSL 3.0在2015年被正式弃用（存在安全漏洞）

**TLS（Transport Layer Security）传输层安全协议**：
- 全称：传输层安全协议
- 开发：由IETF（互联网工程任务组）标准化
- 版本：TLS 1.0、TLS 1.1、TLS 1.2、TLS 1.3
- 状态：目前广泛使用的安全协议标准

**SSL与TLS的关系**：
1. TLS是SSL的继承者：TLS 1.0基于SSL 3.0设计，但做了重要改进，TLS可以看作是SSL的升级版本
2. 命名习惯：虽然现在主要使用TLS，但习惯上仍称为"SSL/TLS"，证书常被称为"SSL证书"，实际使用的是TLS协议

**TLS的优势**：
- 更强的安全性：修复了SSL的安全漏洞
- 更好的性能：TLS 1.3大幅减少了握手时间
- 标准化：由IETF标准化，更规范
- 持续更新：不断修复安全漏洞，推出新版本

**当前使用情况**：
- TLS 1.2：目前最广泛使用的版本
- TLS 1.3：最新版本，性能更好，安全性更高，正在逐步普及
- SSL 3.0及更早版本：已被弃用，存在安全风险

**总结**：TLS是SSL的现代化版本，现在HTTPS实际使用的是TLS协议，但习惯上仍称为SSL/TLS。

## 数据指纹(数据摘要)

**数据指纹（数据摘要）**：通过哈希算法将任意长度的数据转换为固定长度的唯一标识符，类似于数据的"指纹"。

**特点**：
1. **固定长度**：无论输入数据多大，输出的摘要长度固定（如MD5是128位，SHA-256是256位）
2. **唯一性**：理论上不同的数据会产生不同的摘要（哈希碰撞概率极低）
3. **不可逆性**：无法从摘要反推出原始数据（单向函数）
4. **雪崩效应**：原始数据的微小变化会导致摘要的巨大变化

**常见的哈希算法**：
- **MD5**：128位，已被认为不安全（存在碰撞漏洞），不推荐用于安全场景
- **SHA-1**：160位，已被弃用（存在安全漏洞）
- **SHA-256**：256位，目前广泛使用，安全性高
- **SHA-512**：512位，更高的安全性

## 两种加密方式

### 对称加密

**对称加密（Symmetric Encryption）**：加密和解密使用**同一个密钥**的加密方式。

**工作原理**：
- 发送方使用密钥对数据进行加密
- 接收方使用**相同的密钥**对数据进行解密
- 密钥必须保密，只有通信双方知道

**特点**：
1. **加密速度快**：算法简单，计算效率高，适合加密大量数据
2. **密钥管理困难**：通信双方必须安全地共享同一个密钥
3. **密钥分发问题**：如何安全地将密钥传递给对方是一个挑战（密钥传输本身需要加密保护）

**常见算法**：
- **DES**：数据加密标准，已被认为不安全
- **3DES**：三重DES，安全性提高但速度较慢
- **AES**：高级加密标准，目前最广泛使用的对称加密算法（AES-128、AES-192、AES-256）

**应用场景**：
- 适合加密大量数据（如HTTPS中的实际数据传输）
- 需要高性能的场景

**示例**：
```
发送方：明文 + 密钥 → 加密算法 → 密文
接收方：密文 + 密钥 → 解密算法 → 明文
```

### 非对称加密

**非对称加密（Asymmetric Encryption）**：使用**一对密钥**（公钥和私钥）的加密方式，也称为公钥加密。

**工作原理**：
- **公钥（Public Key）**：可以公开，任何人都可以获得
- **私钥（Private Key）**：必须保密，只有密钥拥有者知道
- 用公钥加密的数据，只能用对应的私钥解密
- 用私钥加密的数据，只能用对应的公钥解密

**特点**：
1. **安全性高**：即使公钥泄露，没有私钥也无法解密数据
2. **密钥分发简单**：公钥可以公开传输，不需要保密
3. **加密速度慢**：算法复杂，计算量大，不适合加密大量数据
4. **身份验证**：私钥签名可以验证数据来源的真实性

**常见算法**：
- **RSA**：最广泛使用的非对称加密算法
- **ECC**：椭圆曲线加密，密钥更短，效率更高
- **DSA**：数字签名算法

**应用场景**：
- 密钥交换（如HTTPS握手过程中交换对称加密的密钥）
- 数字签名（验证数据完整性和身份）
- 不适合直接加密大量数据

**示例**：
```
发送方：明文 + 接收方公钥 → 加密算法 → 密文
接收方：密文 + 接收方私钥 → 解密算法 → 明文

数字签名：
发送方：数据 + 发送方私钥 → 签名算法 → 数字签名
接收方：数据 + 数字签名 + 发送方公钥 → 验证算法 → 验证结果
```

**两种加密方式的对比**：

| 特性 | 对称加密 | 非对称加密 |
|------|---------|-----------|
| 密钥数量 | 1个（共享密钥） | 2个（公钥+私钥） |
| 加密速度 | 快 | 慢 |
| 密钥分发 | 困难（需要安全通道） | 简单（公钥可公开） |
| 安全性 | 高（密钥保密前提下） | 高（基于数学难题） |



## 中间人攻击（Man-in-the-Middle Attack）

**中间人攻击（MITM）**：攻击者在通信双方之间拦截、窃听、篡改或伪造数据，而通信双方却认为他们在直接通信。

### 攻击原理

1. **拦截通信**：攻击者位于客户端和服务器之间的网络路径上
2. **伪装双方**：
   - 对客户端伪装成服务器
   - 对服务器伪装成客户端
3. **转发数据**：在双方之间转发数据，同时可以查看、修改或记录所有通信内容


## 加密方案的讨论
### 只采用对称加密
单独采用对称加密，没办法确保安全的将对称密钥交给对方，在这方面比较难保证安全。

**问题**：
- 密钥分发困难：如何安全地将密钥传递给对方？
- 密钥传输本身需要加密保护，形成"鸡生蛋，蛋生鸡"的问题
- 如果通过不安全的通道传输密钥，攻击者可以截获密钥，从而解密所有通信

### 只采用非对称加密
单独采用非对称加密，无法防备中间人攻击。无法辨别公钥是否是服务器的。

**问题**：
- **公钥真实性无法验证**：客户端无法确认收到的公钥是否真的属于目标服务器
- **中间人攻击**：攻击者可以伪造公钥，伪装成服务器
- **性能问题**：非对称加密速度慢，不适合加密大量数据
- **成本高**：加密大量数据会消耗大量计算资源


### 非对称加密 + 非对称加密
### 非对称加密 + 对称加密

上述采用非对称加密的方式，都存在中间人攻击的明显漏洞，**核心问题就是无法确认公钥是否是服务器的公钥**。

## 数字证书（Digital Certificate）解决方案

### 证书的诞生

为了解决公钥真实性问题，引入了**数字证书**：

1. **证书申请**：
   - 企业/服务器需要向**CA（Certificate Authority，证书颁发机构）**申请证书
   - 提交自己的相关信息（域名、企业信息等）和**服务器公钥S**
   - CA机构会审核验证申请者的身份和资质

2. **证书颁发**：
   - 审核通过后，CA机构生成数字证书
   - 证书包含两部分：
     - **明文信息**：服务器信息、服务器公钥S、有效期等
     - **数字签名**：CA机构用**CA的私钥C'**对证书明文信息进行签名

### 证书验证过程

当客户端请求连接服务器时，服务器会发送证书给客户端，客户端进行以下验证：

**步骤1：接收证书**
- 服务器将证书（包含明文信息和数字签名）发送给客户端

**步骤2：验证证书完整性**
```
1. 用CA机构的公钥C解密证书的数字签名
   → 得到散列值H1（这是CA机构对证书明文信息的原始摘要）

2. 对证书的明文信息使用相同的哈希算法（如SHA-256）进行运算
   → 得到散列值H2（这是客户端自己计算的摘要）

3. 比较H1和H2：
   - 如果H1 == H2：证书没有被篡改，有效 ✓
   - 如果H1 ≠ H2：证书被修改过，无效 ✗
```

**步骤3：验证证书有效性**
- 检查证书是否过期
- 检查证书是否被吊销
- 检查域名是否匹配

**步骤4：信任CA机构**
- 客户端需要预先信任CA机构的公钥C
- 操作系统和浏览器内置了可信CA机构的公钥列表

### HTTPS完整握手流程

**证书验证通过后，进行密钥交换**：

1. **客户端验证证书**：确认服务器公钥S的真实性
2. **客户端生成对称密钥K**：随机生成一个对称加密的密钥
3. **客户端加密密钥**：使用服务器的公钥S加密对称密钥K
   ```
   密文 = 加密(对称密钥K, 服务器公钥S)
   ```
4. **客户端发送加密密钥**：将加密后的对称密钥K发送给服务器
5. **服务器解密密钥**：使用服务器的私钥S'解密，得到对称密钥K
   ```
   对称密钥K = 解密(密文, 服务器私钥S')
   ```
6. **双方使用对称密钥通信**：后续所有数据传输都使用对称密钥K进行加密

### 为什么这个方案安全？

1. **防止中间人攻击**：
   - 攻击者无法伪造CA机构的签名（没有CA的私钥C'）
   - 即使攻击者修改证书内容，客户端验证时会发现散列值不匹配
   - 攻击者无法获得服务器的私钥S'，无法解密对称密钥K

2. **性能优化**：
   - 非对称加密只用于密钥交换（少量数据）
   - 对称加密用于实际数据传输（大量数据，速度快）

3. **身份验证**：
   - 证书包含服务器的身份信息
   - CA机构验证了服务器的真实身份

## TLS握手流程详解

### TLS 1.2 握手流程（完整版）

TLS 1.2的握手过程需要**4次往返（RTT）**：

```
1. 客户端 → 服务器：Client Hello
   - 支持的TLS版本
   - 支持的加密套件（Cipher Suites）
   - 客户端随机数（Client Random）
   - 支持的压缩算法

2. 服务器 → 客户端：Server Hello
   - 选择的TLS版本
   - 选择的加密套件
   - 服务器随机数（Server Random）
   - 服务器证书（包含服务器公钥）
   - Server Hello Done

3. 客户端 → 服务器：
   - 验证服务器证书
   - 生成预主密钥（Pre-Master Secret）
   - 用服务器公钥加密预主密钥，发送给服务器
   - 客户端密钥交换（Client Key Exchange）
   - 改变加密规范（Change Cipher Spec）
   - 客户端握手完成（Finished）

4. 服务器 → 客户端：
   - 用服务器私钥解密预主密钥
   - 双方根据Client Random、Server Random、Pre-Master Secret计算主密钥（Master Secret）
   - 改变加密规范（Change Cipher Spec）
   - 服务器握手完成（Finished）

5. 开始加密通信
```

**关键点**：
- **预主密钥**：客户端随机生成，用服务器公钥加密传输
- **主密钥**：由Client Random + Server Random + Pre-Master Secret计算得出
- **会话密钥**：从主密钥派生，用于实际数据加密

### TLS 1.3 握手流程（优化版）

TLS 1.3大幅优化，只需要**1次往返（1-RTT）**，甚至支持**0-RTT**：

```
1. 客户端 → 服务器：Client Hello
   - 支持的加密套件
   - 客户端随机数
   - 支持的密钥交换算法
   - 客户端密钥共享（Client Key Share）- 新特性

2. 服务器 → 客户端：Server Hello
   - 选择的加密套件
   - 服务器随机数
   - 服务器证书
   - 服务器密钥共享（Server Key Share）
   - 服务器握手完成（Finished）

3. 客户端 → 服务器：
   - 客户端握手完成（Finished）

4. 开始加密通信
```

**TLS 1.3的优势**：
- **更快的握手**：从4次往返减少到1次往返
- **更强的安全性**：移除了不安全的加密算法
- **前向安全性**：默认支持前向安全性（Forward Secrecy）
- **0-RTT模式**：对于已访问过的网站，可以实现0-RTT连接

## 证书链（Certificate Chain）

**证书链**：从服务器证书到根CA证书的完整信任链。

### 证书层级结构

```
根CA证书（Root CA）
    ↓ 签名
中间CA证书（Intermediate CA）
    ↓ 签名
服务器证书（Server Certificate）
```

**为什么需要证书链？**

1. **安全性**：根CA的私钥非常敏感，不能频繁使用
2. **灵活性**：中间CA可以用于不同用途（如不同地区、不同业务）
3. **吊销管理**：如果中间CA出现问题，只需吊销中间CA，不影响根CA

### 证书链验证过程

客户端需要验证整个证书链：

1. **验证服务器证书**：用中间CA的公钥验证服务器证书
2. **验证中间CA证书**：用根CA的公钥验证中间CA证书
3. **信任根CA**：根CA的公钥预装在操作系统/浏览器中
4. **构建信任链**：从服务器证书到根CA的完整信任路径

**常见问题**：
- **证书链不完整**：服务器只发送了服务器证书，没有发送中间CA证书
- **解决方案**：服务器需要发送完整的证书链（服务器证书 + 中间CA证书）

## 证书类型

### DV证书（Domain Validated）
- **验证级别**：最低，只验证域名所有权
- **验证方式**：通过DNS或HTTP验证域名控制权
- **颁发速度**：几分钟到几小时
- **价格**：最便宜，甚至免费（如Let's Encrypt）
- **适用场景**：个人网站、小型网站

### OV证书（Organization Validated）
- **验证级别**：中等，验证域名所有权 + 组织信息
- **验证方式**：需要提供企业营业执照等文件
- **颁发速度**：1-3天
- **价格**：中等
- **适用场景**：企业网站、商业网站

### EV证书（Extended Validation）
- **验证级别**：最高，严格验证企业身份
- **验证方式**：需要提供详细的企业资质文件，人工审核
- **颁发速度**：3-7天
- **价格**：最贵
- **特点**：浏览器地址栏显示绿色企业名称
- **适用场景**：银行、金融机构、大型企业

## 前向安全性（Forward Secrecy）

**前向安全性（Perfect Forward Secrecy，PFS）**：即使长期私钥泄露，也无法解密之前捕获的加密通信。

### 为什么需要前向安全性？

**问题场景**：
- 攻击者长期监听并记录所有加密通信
- 如果未来服务器的私钥泄露，攻击者可以用私钥解密之前记录的所有通信

**解决方案**：
- 每次会话使用**临时密钥**（Ephemeral Key）
- 即使长期私钥泄露，也无法解密之前的会话
- TLS 1.3默认支持前向安全性

### 实现方式

**ECDHE（Elliptic Curve Diffie-Hellman Ephemeral）**：
- 每次握手时，客户端和服务器各自生成临时的密钥对
- 通过密钥交换算法，双方计算出共享的会话密钥
- 会话结束后，临时密钥被丢弃
- 即使长期私钥泄露，也无法恢复之前的会话密钥

## HSTS（HTTP Strict Transport Security）

**HSTS**：强制浏览器使用HTTPS连接，防止降级攻击。

### 工作原理

服务器在HTTPS响应头中发送：
```
Strict-Transport-Security: max-age=31536000; includeSubDomains
```

**效果**：
- 浏览器在指定时间内（max-age）强制使用HTTPS访问该域名
- 即使输入`http://`，浏览器也会自动转换为`https://`
- `includeSubDomains`：包括所有子域名

### 为什么需要HSTS？

**降级攻击（Downgrade Attack）**：
- 攻击者拦截HTTP请求，阻止用户访问HTTPS
- 强制用户使用HTTP，从而窃听或篡改数据
- HSTS可以防止这种攻击

## SNI（Server Name Indication）

**SNI**：在TLS握手时，客户端告诉服务器要访问的域名。

### 为什么需要SNI？

**问题**：一个IP地址可能托管多个HTTPS网站（虚拟主机）

**没有SNI的情况**：
- 服务器不知道客户端要访问哪个域名
- 只能返回默认证书，可能导致证书不匹配错误

**有SNI的情况**：
- 客户端在Client Hello中发送要访问的域名
- 服务器根据域名返回对应的证书
- 支持一个IP地址托管多个HTTPS网站

### 限制

- **不支持SNI的旧客户端**：Windows XP的IE、Android 2.x等
- 这些客户端无法访问使用SNI的网站

## 常见攻击和防护

### BEAST攻击（Browser Exploit Against SSL/TLS）

**攻击方式**：利用CBC模式的漏洞，逐步解密HTTPS通信。

**防护**：
- 使用TLS 1.1+（修复了CBC漏洞）
- 使用RC4或AES-GCM模式

### POODLE攻击（Padding Oracle On Downgraded Legacy Encryption）

**攻击方式**：强制降级到SSL 3.0，利用填充漏洞。

**防护**：
- 禁用SSL 3.0
- 使用TLS 1.0+

### Heartbleed漏洞

**攻击方式**：利用OpenSSL的Heartbeat扩展漏洞，读取服务器内存。

**防护**：
- 及时更新OpenSSL
- 更换证书和私钥

### FREAK攻击（Factoring Attack on RSA-EXPORT Keys）

**攻击方式**：利用弱RSA密钥（512位）的漏洞。

**防护**：
- 禁用弱加密套件
- 使用强密钥（2048位以上）

## 面试重点总结

### 核心知识点

1. **HTTPS = HTTP + TLS/SSL**
2. **混合加密**：非对称加密交换密钥 + 对称加密传输数据
3. **数字证书**：解决公钥真实性问题，防止中间人攻击
4. **TLS握手流程**：TLS 1.2（4次往返）vs TLS 1.3（1次往返）
5. **证书链**：从服务器证书到根CA的完整信任链
6. **前向安全性**：即使私钥泄露，也无法解密之前的通信
7. **HSTS**：强制使用HTTPS，防止降级攻击
8. **SNI**：支持一个IP托管多个HTTPS网站

### 常见面试问题

1. **HTTPS是如何保证安全的？**
   - 加密（对称+非对称）、完整性（哈希）、身份验证（证书）

2. **为什么需要数字证书？**
   - 解决公钥真实性问题，防止中间人攻击

3. **TLS 1.2和TLS 1.3的区别？**
   - 握手次数：4次 vs 1次
   - 安全性：TLS 1.3更强
   - 前向安全性：TLS 1.3默认支持

4. **什么是中间人攻击？如何防护？**
   - 攻击者拦截通信，伪造身份
   - 通过数字证书验证服务器身份

5. **HTTPS的性能影响？**
   - 握手延迟、CPU开销
   - 通过会话复用、TLS 1.3等优化
